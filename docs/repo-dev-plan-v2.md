## 1. 개발 절차 (모든 신규 기획에 적용)

```
① 기획 수신        원문을 docs/specs/에 보관 (PDF는 텍스트로 전사)
② 계획 작성        docs/plans/NNN-<기능>.md  ← 코드 작성 전
③ 결정 확인        "확정 필요" 항목을 운영 담당자에게 확인. 미확정이면 임시 기준을 계획에 명시
④ 브랜치           feat/NNN-<기능>
⑤ 구현             model.ts → adapters.ts → components.tsx → 연결 순서. 테스트는 model과 함께 작성
⑥ 검증             pnpm test + tsc + 계획 문서의 화면 검수
⑦ 문서 갱신        계획 문서의 추적표 상태 갱신, README 문서 목록·검증 명령 갱신
⑧ 커밋·PR          작업 패키지 단위. PR 본문에 추적표 링크
```

### 계획 문서 양식 (`docs/plans/NNN-<기능>.md`)

```markdown
# NNN. <기능명> 개발 계획
- 근거: docs/specs/<원문>
- 상태: 계획 | 진행 | 완료   · 브랜치: feat/NNN-...

## 요구사항 추적표
| ID | 기획 원문 요약 | 구현 위치(파일) | 검증(테스트/화면) | 상태 |

## 데이터 영향
기존 필드로 가능한 것 / 새 필드·마이그레이션이 필요한 것 / Edge 번들 재생성 여부

## 확정 필요 결정
| 항목 | 임시 기준 | 결정권자 |

## 변경 파일 예정
## 검증 계획 (자동 / 화면 수동)
## 범위 밖 (후속)
```

### Phase 3. 데이터 계약 보강 (Supabase 마이그레이션 필요)

운영 DB 변경이므로 항목마다 별도 승인을 받는다. `supabase/schema.sql`은 빈 프로젝트 설치용이라 운영에 재실행하지 않는다. 운영 변경은 **추가 마이그레이션 파일**(`supabase/migrations/<날짜>_<내용>.sql`)로만 하고, 같은 내용을 `schema.sql`에도 반영해 신규 설치와 일치시킨다.

| # | 데이터 | 이유 (막혀 있는 요구) | 변경 범위 |
|---|---|---|---|
| 3-1 | 후속 조치 **심각도** (`severity`, 승인된 등급) | D-05 긴급 지표·우선 노출 | 컬럼, `zf_write` 검증, 입력 폼, `adapters.ts`의 `urgent` 채우기, Edge 번들 |
| 3-2 | 후속 조치 **상태 변경 이력** (생성·완료·재개 시각) | W-03 주말 기준 미해결, W-04 동시간 비교, C-08 재개 | 상태 전이 기록 테이블 또는 `zf_audit` 활용 규칙, `weekDiagnosis` 확장 |
| 3-3 | 재개 시 완료일 처리 규칙 | 현재 `zf_write`는 재개하면 `completedDate`를 지움(`schema.sql:164`) → 과거 해결 건수가 사라짐 | 3-2와 함께 설계 |
| 3-4 | 이슈별 조치 이력 조회 | 운영 모드에서 `zf_read`는 감사 기록을 관리자 또는 본인 작성분, 최근 300건만 돌려줌 → 상세 "조치 이력"이 잡매니저·팀장에게 일부만 보임 | 대상 권한 기준의 이슈별 이력 조회 RPC |
| 3-5 | 사진·첨부 | C-02의 "사진" | 저장소·용량·보관정책·권한 (README 후속 항목과 통합) |

각 항목의 완료 기준: 마이그레이션 + `tests/supabase.sql` 불변조건 추가 + `node scripts/bundle-supabase.mjs` + Edge 재배포 + 운영 모드 화면 확인.
