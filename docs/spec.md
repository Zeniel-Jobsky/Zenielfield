## 1. 방문·일지 워크플로

기준: 2026-10-28.

### 진단 (쓰는 사람 = 잡매니저, 현장·모바일)

- 결과 등록 화면에서 대상 선택이 3번 겹침: 계획 연결 셀렉트 · 현장/매장 전환 · 현장·매장 셀렉트 · GPS
- 계획이 있어도 기본값 "계획 외 방문" → 연결 누락 → 회차 미충족
- 실제 방문일·시간을 매번 입력. 현장에서는 "지금"이 기본이어야 함
- 후속 조치 필요 → 저장 후 두 번째 입력창이 또 열림. AI가 제안한 조치를 체크했는데 다시 입력
- 권한 카드가 매번 크게 노출
- 홈에서 "지금 여기" 바로 기록하는 진입점 없음

### 진단 (보는 사람 = 팀장·파트장·사업부장)

- 대상 상세 이력에 AI 요약·긴급도·GPS 확인 표시 없음 → 목록과 상세 정보 불일치
- 일지(시간순 활동 기록) 개념 없음. 방문 결과 1건 = 상세 텍스트 1개

### 목표 워크플로 (쓰는 사람)

1. 홈 "지금 여기서 방문 기록" 또는 오늘 일정 탭 → 기록 시트 1화면
2. 대상 = GPS 300m 자동 선택 → 그 대상의 미완료 계획 자동 연결(가장 가까운 예정일). 없으면 계획 외
3. 말·사진·글 → AI 초안 → 요약·활동·특이사항·후속 필요만 확인 → 저장
4. 방문 일시 = 지금. 바꿀 때만 펼침
5. 후속 필요 + 제안 조치 체크 → 저장 시 조치 즉시 등록. 두 번째 창 없음
6. 권한 = 허용되면 한 줄. 거부 시만 카드

### 목표 워크플로 (보는 사람)

- 대상 상세 "이력" = 일지. 건마다 AI 요약·분류·긴급도·GPS 거리·연결 조치
- 결과 목록·브리핑·대시보드는 같은 표시 규칙 (`AiLine`)

### 구현 위치

- `ai-form.tsx`: 계획 자동 연결 · 일시 기본 지금 · 일시 접힘
- `app.tsx save()`: 체크한 제안 조치 일괄 등록
- `views.tsx ManagerHome`: "지금 여기서 방문 기록"
- `views.tsx TargetDetail`: 이력에 `AiLine`

### 2026-10-28 보완

- 계획 자동 연결 = 오늘 기준 ±14일 안의 미완료 계획만. 없으면 계획 외 방문 안내
- 연결 표시 줄: "계획 연결" 레이블과 값 간격 분리, 전환 링크 아이콘+간격
- 계획 자동 연결은 오늘 연결 가능한 계획만(필요 회차 인정 기간이 시작된 것). 지난·오늘 계획 우선, 그다음 가까운 예정. 이전에는 미래 계획이 먼저 연결돼 저장이 "필요 회차 시작일 이전" 오류로 막혔음
- 데모 모드는 AI를 부르지 않고 낱말 기반 예시 초안을 만든다(로그인 없이 AI 호출이 막혀 흐름이 끊겼던 문제)
- 잡매니저 홈: 오늘 업무·기록 버튼을 맨 위로, 차트는 아래
- 실측(390px 데모, 잡매니저): 기록 버튼 → 메모 입력 → 초안 → 가까운 지점 선택 → 저장 성공 → 제안 조치 2건 즉시 등록 확인
- 데모 표시 정리: 상단 배너 한 줄로 모으고 홈 배지·폼 안내·변경 이력·브리핑 출처·`[데모 데이터]` 접두어·운영 화면 `데모 보기` 제거
- 모바일 잡매니저 홈: 오늘 업무 머리글 세로 배치, 기록 버튼 전체 폭 48px
- 검증: 390/820/1280px AI 일정 등록·AI 결과 등록·직접 입력, 화면 오류·넘침 없음

### 2026-10-28 기입력 결과 AI 정리

- 위치: 직접 입력 방문 결과 화면 `특이사항` 바로 아래 `AI로 문장 정리` 버튼 한 줄(처음엔 폼 맨 아래라 안 보였고, 입력칸 위에 두니 제목·버튼 중복과 순서가 어색해 재배치) (`app/platform/form.tsx` `AiTidy`)
- 흐름: 현재 칸 값 읽기 → `/api/assist` `mode:'tidy'`(사실·수치 유지, 문장만 정리) → 바뀌는 칸만 현재/제안 + 체크(기본 체크) → `선택한 칸 반영`이 폼 값을 바꿈 → 저장 시 `aiEdit`(model·generatedAt·before·proposed) 전달 → 서버(`mutations.ts`)가 저장값이 제안과 같고 이전값과 다른 칸만 `applied`로 계산해 `aiEdits[]`에 추가(최근 10개, byId·appliedAt) → 목록·이력에 `AI 정리 n회` 배지(title에 반영 칸)
- 되돌리기: 저장 전에는 `되돌리기`로 before 값 복원, 저장 후에는 기록이 남는다(수정은 일반 수정 + 새 정리)
- 제약: `entry`는 바뀌지 않음(직접 입력은 manual 유지). 클라이언트가 보낸 `aiEdits`는 무시. 방문 결과(completed)에만. DB 제약 `zf_visits_ai_edits_array`(`20261028130000_ai_edits.sql`)
- 데모: 서버 호출 없이 공백·문장부호 정리 + 후속 키워드 판정(`데모 예시 정리`)
- 실측(390·1280 데모): 입력 → 제안 3칸 → 반영 → 저장 → 후속 조치 입력 이어짐 → 방문 결과 목록 `AI 정리 1회` 배지, 테스트 `platform-invariants` 5건 추가(기록·중복 방지·클라이언트 값 무시·계획에는 불가)

### 2026-10-28 음성 입력 반복 단어 수정

- 증상: 음성으로 입력하면 같은 단어·문장이 반복해서 들어감(특히 휴대폰 Chrome)
- 원인: 인식 결과를 받을 때마다 확정 문장을 이어 붙였는데, 브라우저가 이미 확정된 결과를 다시 보내거나 앞 문장을 포함한 누적 결과를 보냄
- 수정(`app/platform/ai-assist.tsx`): 매번 전체 결과 목록으로 다시 만들고, 앞 결과를 포함하는 결과는 앞 결과를 대체, 이미 들어간 결과는 건너뜀. 녹음 시작 전 입력은 그대로 유지
- 검증: 누적·중복 결과를 보내는 가짜 인식기로 "현장 도착 안내문 교체 요청 후 재확인함" 한 번만 입력되는 것 확인. 실제 기기 음성은 사용자 확인 필요

### 2026-10-28 반복 말 정리 · AI 연결 실패 대체

- 반복 말: `collapseRepeats`(app/lib/dedupe-text.ts)가 연속된 같은 단어·구절(최대 8낱말)·문장을 하나로 줄임. AI 입력·일정 등록 전송 전, 서버(result/plan/tidy), 간단 정리에 적용. 테스트 9건

## 2. 플랫폼 연결·데이터 명세

기준: 2026-10-26. 기존 Site를 유지한 1차 UX/UI 구현. 기존 API·DB·인증·마이그레이션·접근범위 설정은 변경하지 않았다.

### 구현 경계

| 영역 | 현재 동작 | 실제 운영 연결 |
|---|---|---|
| 기존 로그인·현장·방문·후속 조치 | 기존 서버/API/저장 기능 보존 | `기존 실제 운영 열기`에서 사용 |
| 확장 통합 대시보드 | 30명·100현장·500매장 초기 데모에서 자동 집계 | 매장·회차 데이터 계약 구현 필요 |
| 현장·매장 계층 및 개별 등록/수정 | 브라우저 메모리의 가상 데이터 | 새로고침 시 초기화; 기존 DB로 보내지 않음 |
| 현장/매장 공동 담당 | 각 대상의 `managerIds` 배열, 변경값 감사 기록 | 관계 테이블과 배정 유효기간 필요 |
| 방문계획·실제 결과·연결 이슈 | 데모에서 전체 흐름 동작 | 대상 유형 및 매장ID를 서버 계약에 추가 |
| 통계·CSV·인쇄 | 화면 조회 및 UTF-8 BOM CSV, 현재 화면 인쇄 | XLSX 전용 서식 및 정식 보고서 템플릿은 후속 |
| 사진·첨부·자동 알림 | 미구현임을 화면에 표시 | 저장소·파일검증·권한·보관정책·전송 설정 필요 |

실제 운영 데이터에 매장 방문을 현장 방문으로 변환해 저장하는 우회 동작은 없다. 확장 화면은 `데모 데이터`로 표시하며 기존 실제 운영과 분리한다.

### 데이터 계약

운영용 변경은 별도 승인 후 추가 마이그레이션으로 구현해야 한다. 기존 테이블을 초기화하거나 이전 마이그레이션을 수정하지 않는다.

- 조직: 사업부 → 팀 → 파트 → 사용자. 운영용 조직 고유 ID, 상위 조직 ID 및 배정 유효기간 필요.
- 현장: `site_id`, 고유코드, 고객사, 조직 ID, 주소/지역, 상태, 운영 시작일.
- 매장: `store_id`, `site_id`, 고유코드, 매장명, 주소/지역, 상태, 운영 시작일. 반드시 기존 상위 현장 참조.
- 대상 배정: 현장/매장 유형과 대상 ID, 사용자 ID, 주/공동 담당 구분, 배정 시작/종료일. 한 대상에 복수 담당 가능. 과거 방문자는 변경하지 않음.
- 방문 주기 정책: 대상 유형·ID, 주/월/수동, 주기당 필요 횟수, 적용 시작/종료일, 정책 버전.
- 필요 방문 회차: 고유 ID, 대상 유형·ID, 정책 버전, 인정 기간 시작/종료, 회차 기한, 순번. 정책 변경 전에 생성된 회차는 이력 보존.
- 방문 기록: 고유 방문 ID, `targetType`, `siteId`, 매장 방문에만 `storeId`, 방문자 ID, 계획 일시, 실제 일시, 상태, 목적, 결과, 특이사항, 연결 필요회차 ID.
- 후속 조치: 고유 이슈 ID, 동일한 대상 식별자, 관련 방문 ID, 유형, 내용, 담당자, 등록일, 기한, 상태, 완료일.
- 감사 기록: 작성/수정자, 대상, 변경 전/후 값, 시각, 수정 사유. 서버에서 작성하며 클라이언트 값을 그대로 신뢰하지 않음.

### 핵심 불변조건

1. 현장 자체 방문의 `storeId`는 null. 매장 방문은 `storeId`가 필수이며 해당 매장의 `siteId`와 일치한다.
2. 본사 방문 한 건을 산하 매장 전체 방문으로 확장하지 않는다. 다른 매장을 언급한 보고서도 같은 원칙이다.
3. 한 방문 기록은 최대 한 필요 회차만 충족한다. 반복 방문은 모두 저장하며 잉여 방문은 별도 실적으로 확인한다.
4. 계획 취소는 필요 회차를 제거하지 않는다. 활성 계획·완료 기록이 없으면 계획 미등록으로 복귀한다.
5. 예정일 경과는 지연이다. 실제 결과가 없으면 완료로 변경하지 않는다.
6. 완료·취소 방문은 임의로 상태를 되돌리거나 다른 대상으로 옮기지 않는다. 보정은 감사 이력을 갖는 명시적 절차가 필요하다.
7. 담당자 변경으로 과거 방문자·결과를 덮어쓰지 않는다. 기존 미래 계획의 방문자 변경은 별도 명시적 작업이다.
8. 공동 담당자별 화면에는 같은 대상이 표시될 수 있다. 사업부/팀 합계를 담당자 행의 단순 합으로 계산하지 않는다.
9. 관련 이슈의 대상과 관련 방문의 대상은 동일해야 한다.
10. 이력이 없으면 미확인으로 표시한다. 등록일·방문일을 추정해 만들지 않는다.

### 이행률 및 기간 정책

현재 데모는 다음 규칙을 명시적으로 사용한다. 정식 운영 전 운영부서와 확정해야 한다.

- 필요 회차는 주/월 내 요구 횟수를 날짜 구간으로 균등 분할한다. 예: 31일인 달의 월 2회는 1–15일, 16–31일.
- 주간은 월요일부터 일요일. 주간 1–7회, 월간 1–8회, 수동 관리 지원.
- 기한이 조회 기간에 들어오는 필요 회차를 분모로 한다. 해당 필요 회차 중 조회 시점까지 실제 결과로 충족된 회차를 분자로 한다.
- 따라서 이것은 `회차 기한 기준 이행률`이며 단순한 실제 방문일 기준 건수와 구분된다. 실제 방문일 기준 기록은 방문 결과·이력에서 조회한다.
- 기한이 지난 회차의 사후 완료는 그 회차와 명시적으로 연결되면 완료로 인정한다. 계획 외 방문은 해당 인정 기간의 아직 충족되지 않은 회차 1개에만 대응할 수 있다.
- 필요 회차가 0이면 이행률은 ‘—’. 수동 관리 대상은 자동 분모에서 제외한다.
- 정상 분류 합계: 필요 = 완료 + 예정 + 지연 + 계획 미등록.
- 매장 커버리지 = 조회 기간에 실제 방문한 고유 매장 수 / 조회 범위 매장 수. 회차 이행률과 다른 지표다.
- 일정 취소 후 회차 재등록, 공동 방문 한 회차의 대표 방문기록, 비영업일·공휴일·휴점·중도 오픈·조직 이관은 운영 정책을 추가 확정해야 한다.
- 데모 정책 수정은 현재 규칙으로 재계산한다. 운영 시스템에서는 정책과 필요 회차의 버전·이력 스냅샷을 반드시 보존해야 한다.

- 실제 방문일이 있는 완료 기록만 주간 활동으로 인정한다. 계획·취소·미래 실제일은 제외한다.

- 역할 권한 범위보다 넓은 대상을 요청하거나 조회하는 별도 API는 없다. 매장만 권한이 있는 경우 권한 있는 매장 기록만 상위 현장명 아래 표시한다.
- 현장명 검색은 산하 매장 포함, 매장명 검색은 해당 매장, 방문자 검색은 해당 방문자가 작성한 활동을 조회한다.

- 활동 없는 주차는 빈 상태. 과거 기록을 현재 활동으로 보정하지 않는다.

- 카드 정렬: 기한 초과 → 미해결 → 지연 → 최근 활동. 실제 활동 있는 현장 중 최대 3개.

## 5. 방문·조치 한 화면 설계

### 문제
- 방문 기록(현장에서 본 것)과 후속 조치(누가 언제까지 해결)는 같은 이슈의 앞뒤인데 메뉴 둘로 나뉨 → 한 현장 이슈를 따라가려면 두 메뉴 왕복
- 입력이 흩어짐: 결과 등록·후속 조치 추가·조치 수정이 서로 다른 화면·다른 모양 버튼
- 뜻 없는 기호: `+`(무엇을 더하나), `›`(어디로 가나)만 단독 사용

### 근거
- 화면·과업 분절은 판단을 흐림: 진료기록 연구에서 정보가 여러 화면·목록으로 나뉘면 판단이 구조에 끌려가고 왕복이 늘어남(Senathirajah 외 2020, JMIR, PMC7641790)
- 관련 동작은 기준 거래로 돌아가지 않게 한 곳에(엔터프라이즈 내비게이션 특허·Microsoft Dynamics 과업 중심 화면: 자주 쓰는 명령을 그 과업 화면에)
- 메뉴는 기능(명사)보다 일(동사) 기준으로(Microsoft Fluent nav 가이드, B2B CX 실무서)
- 아이콘만으로는 뜻 전달이 약함: 라벨 없는 앱 고유 아이콘 정답률 34%, 라벨 있으면 크게 오름(UserTesting 인용). 보편 인식 아이콘은 홈·인쇄·검색 정도(NN/g 인용) → 아이콘 + 글자
- 한계: 현장 방문 보고 화면을 직접 비교한 연구 없음. 위 근거는 인접 분야·실무 자료

### 설계
- 메뉴 `방문 기록` + `후속 조치` → `방문·조치` 하나(페이지 키 `results` 유지, `actions` 진입은 같은 화면 조치 탭으로)
- 맨 위 제니에리 정리 하나: 무슨 일(방문 현황 문단 · 조치 현황 문단) → 이렇게 챙겨 보세요(결과 안 쓴 방문·기한 넘긴 조치를 오래된 순 섞어 3건)
- 탭 한 줄: 방문 `전체 방문` · `결과 안 쓴 방문` · `먼저 볼 보고` · `고객 요청` │ 조치 `안 끝난 조치` · `기한 넘긴 조치` · `완료 조치`
- 방문 목록: 방문 줄 아래 그 방문에서 생긴 조치를 들여 쓴 하위 줄(유형·내용·담당·기한·상태). 조치 목록은 기존 표
- 입력은 이 화면 한 곳: 상단 `방문 결과 등록`, 줄마다 `결과 쓰기`·`조치 추가`·`조치 수정`
- 기호 대신 아이콘 + 글자(Lucide 16px): 결과 쓰기 `PenLine` · 결과 보기 `FileText` · 조치 추가 `ClipboardPlus` · 일정 잡기 `CalendarPlus` · 보낼 말 복사 `Copy`+`보낼 말` · 현장 보기 `MapPin`. 조치 수정·보기 링크는 `후속조치 수정`·`후속조치 보기` 제목 바로 뒤 `ChevronRight` 14px. 단독 `+`·`›` 금지
- 데이터·서버 변경 없음(화면에서 묶어 보여 줌)

### 검증
- 390/820/1280, 관리자·잡매니저, 탭 전환·하위 조치 줄·버튼 동작, 타입·테스트
