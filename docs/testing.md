## 로컬 프로그램 테스트 계획

_원래 문서: `docs/program-test-plan.md` (2026-10-30 통합)_

기준일: 2026-10-28
대상: http://127.0.0.1:5173/
상태: 계획 수립. 브라우저 접속, 자동 검사, 운영 검증은 미실행.
근거: AGENTS.md, PROJECT_RULE.md, 디자인 지침, package.json, tests/ 실행 파일.
기존 기능 현황의 통과 횟수는 과거 기록이며 이번 실행 결과가 아니다.

### 목표와 준비

방문계획 → 방문결과 → 후속 조치 → 브리핑의 정확성과 역할별 데이터 격리를 최우선으로 확인한다.
실행 전 커밋·작업 트리·푸터 빌드 정보, 브라우저 버전, 인증 제공자, 데이터 모드를 기록한다.
데모 및 격리된 테스트 데이터로 시작한다. 로컬 주소라도 공용 Supabase에 연결될 수 있다.
운영 DB 쓰기·계정 발급·Edge 배포는 기존 규칙에 따라 별도 승인 대상이다.
기존 계정이 없으면 인증 검증은 차단으로 기록하며 임의로 계정을 만들지 않는다.

역할 이름과 허용 범위는 실행 전 코드 및 승인된 권한표로 확정한다.
집계는 수기 검산 가능한 고정 표본을 준비한다. 예: 필요 4회차·인정 완료 3회차이면 75%.
회차 인정 방식은 model 규칙에 맞춰 표본을 구성하며 방문 건수를 회차로 대체하지 않는다.

### 화면 검증

390·820·1280px에서 핵심 흐름을 각각 수행하고 200% 확대를 확인한다.
760/761·1023/1024·1439/1440px 경계는 배치 전환을 추가 점검한다.
기본·hover·focus·active·disabled·loading·empty·error 상태를 확인한다.
키보드 이동·대화상자 포커스 복귀·44px 터치 영역·레이블·대비·잘림을 검증한다.
딥그린 강조, 상태색, 축·범례 12px, 모바일 제목 26px, 탭 간격과 차트 원본 이동을 확인한다.
잡매니저 홈 순서는 AGENTS.md를 우선한다. PROJECT_RULE.md 요약과의 순서 차이는 기준 불일치 이슈로 기록한다.

### 자동 검사와 순서

1. 환경·데이터 연결 확인 및 T01~T04 진입·권한 점검.
2. npm run typecheck, npm test 실행. 현재 npm test는 platform·briefing·diagnosis·supabase·logic·ui-metrics 6개 묶음이다.
3. 위치·시드·인증 추가 검증: tests/run-geo.mjs, run-seed.mjs, run-cloudflare-auth.mjs, run-cloudflare-supabase.mjs를 node로 실행한다. 실행 전 외부 연결·쓰기 여부를 점검한다.
4. T05~T16 및 반응형·접근성 수동 검증.
5. npm run build 실행 및 빌드 산출물 확인. 패치 버전 자동 증가를 기록하며 검증용으로 생략할 때는 PowerShell에서 NO_BUMP=1 환경변수를 임시 설정하고 복구한다.
6. 결함 수정 후 실패 사례와 영향 범위를 재검증한다. UI 수정은 지침·두 룰 갱신 및 실제 화면 재검증을 동반한다.

API·인증 모의 테스트 통과는 실제 Supabase 로그인·권한 검증을 대신하지 않는다.
초기 실행 예상은 환경 준비 0.5일, 업무·권한 1일, 화면·회귀 0.5일이다. 수정 시간과 계정 대기는 별도다.

### 완료와 증적

P0 전부 통과, 데이터 유실·권한 누출·집계 오류 0건을 필수로 한다.
미해결 P1은 영향·우회 방법·출시 허용 판단을 기록한다. 차단·미실행은 통과로 세지 않는다.
각 결과는 ID / 환경·역할 / 사전 데이터 / 절차 / 기대·실제 / 통과·실패·차단·미실행 / 증적 / 결함 ID로 기록한다.
스크린샷·네트워크 증적은 개인정보·토큰을 제거한다. 최종 보고에는 커밋·빌드·화면 크기·검사 결과를 포함한다.

### 2. 최신성 및 변경 관리

1. 실행 시작 시 HEAD, 브랜치, 미커밋 변경, 원격 기준 리비전을 기록한다. 원격 비교 전에는 최신 원격 소스라고 표시하지 않는다.
2. 사용자의 작업을 보존하며 원격 차이를 검토한다. 자동 병합이나 강제 초기화로 테스트 기준을 맞추지 않는다.
3. 테스트 기준은 커밋과 미커밋 diff의 조합으로 고정하고 시작·종료 시 변경 여부를 비교한다.
4. 개발 서버 시작 리비전·푸터·실제 소스의 대응을 확인한다. 필요하면 서버를 재시작한 뒤 브라우저를 새로 로드한다.
5. 실행 중 소스가 바뀌면 영향받는 통과 결과를 재검증 대상으로 돌린다. 서로 다른 리비전의 결과를 합산하지 않는다.
6. 변경 파일→영향 기능→재실행 사례를 기록한다. model/mutations/API/권한 변경은 모든 P0를 재검증한다.

이전 관찰: 로컬 HEAD ec01a31, 서버 푸터 87f606c. 푸터만으로 실제 코드 노후화를 단정하지 않는다.
기존 문서와 다른 구현은 무조건 오류로 판정하지 않는다. 최신 명시 요구, 업무 불변 조건, 구현 의도와 대조해 결함/의도된 변경/기준 미확정으로 구분한다.
현재 코드는 시험 대상이며, 현재 동작 자체를 정답으로 삼지 않는다.

### 3. 환경과 데이터

데모: 화면 전환·입력·역할 시연 검증. 서버 권한이나 실제 저장 증거로 대체하지 않는다.

### 5. 상세 사례 양식

사례 ID / 기준 리비전·변경분 / 요구사항 근거 / 역할·모드 / 준비 데이터 /
조작 순서 / 기대값 / 실제값 / 상태 / 증적 / 결함 번호 / 재검증 리비전.

예시 ACL-02-A:
- 사전 조건: 격리 환경 사업부장 계정, 변경 전 기록 확보.
- 조작: 동일 대상의 쓰기 요청을 정상 클라이언트와 직접 API 경로에서 각각 시도.
- 기대: 서버가 거부하고 데이터·감사 기록에 성공 변경이 없음.
- 상태: 미실행. 응답 코드는 해당 서버의 명세 확인 후 확정.

집계 예상값은 테스트 대상 함수를 그대로 호출해 만들지 않고 독립 표본으로 계산한다.
UI 문서와 구현 차이, 도구 오류, 제품 오류를 별도 분류한다.

### 6. 실행 단계와 측정

A. 기준 확정: 리비전·환경·역할·현재 요구사항 및 테스트 데이터 확정.
B. 정적/자동: npm run typecheck, npm test. 현재 기본 테스트 6개 묶음 확인.
C. 추가 회귀: run-geo, run-seed, run-cloudflare-auth, run-cloudflare-supabase. 외부 연결·쓰기 여부 확인 후 실행.
D. 핵심 업무: P0 전체, P1 저장·복구·AI·보고 순서. 각 역할의 API 검증 포함.
E. 실제 화면: 390/820/1280px 및 필요한 200% 확대, 760/761·1023/1024·1439/1440 경계.
F. 빌드: npm run build. 패치 버전 자동 증가를 기록하거나 검증용 NO_BUMP=1을 임시 적용·복구.
G. 결함 수정 이후 해당 사례와 영향 범위 회귀, 종료 시 소스 변경 여부 확인.

키보드 이동·대화상자 닫기·포커스 복귀, 44px 터치 영역, 레이블·대비를 검증한다.
기본/hover/focus/active/disabled/loading/empty/error 상태를 포함한다.
성능은 동일 장비·데이터에서 최초/재방문 로딩과 필터 반응을 각각 10회 측정하고 중앙값·최댓값을 기록한다.
성능 통과 수치는 현재 근거가 없어 미확정이다. 기준 측정 후 목표를 정하며 임의로 통과시키지 않는다.
사용성 지표는 핵심 시나리오 완료율·오류 횟수·복구 성공 여부다. 실제 사용자 평가는 별도 세션으로 구분한다.

### 8. 기준 비교 및 최종 적용 (2026-10-28)

사용자가 말한 Astra 제안은 이 대화에서 작성한 최신 소스 기반 테스트 계획을 뜻한다.
판단: 실행·합격 판정은 이 대화의 소스 기반 계획을 중심으로 하고, 프롬프트의 요구사항 추적과 사용성 측정을 보완 기준으로 결합한다.
아래 비교는 실제 테스트 효과의 실험 결과가 아니라 문서의 구체성·적합성에 대한 검토다.

#### 최종 보강 기준

1. 요구사항 상태를 확정/가정/충돌로 표시한다. 확정 요구만 합격 판정에 사용하고 가정·충돌은 관찰 결과와 분리한다. 원문 위치와 채택 이유를 기록한다.
2. 사례마다 정상·거부·경계·실패 복구 중 적용되는 분류를 기입한다. 권한 거부는 화면 버튼 숨김뿐 아니라 API 응답과 변경 전후 데이터로 증명한다.
3. 권한은 5개 역할 × 담당/타조직/타도메인 × 읽기/쓰기의 적용 가능한 조합을 명시한다. 적용 제외에는 이유를 남기며 미작성 조합을 통과로 세지 않는다.
4. 저장 성공은 성공 알림만으로 판정하지 않는다. 새 조회와 새 세션에서 값·원본 연결·이력 보존을 확인한다. 화면·서버·저장소 증거의 실제 확보 범위를 기록한다.
5. AI의 문장 표현은 고정 문자열로 비교하지 않는다. 원본 수치·기간·대상·선택 반영·개인정보·실패 시 대체 동작을 검증한다.
6. 성능 10회 측정은 탐색용 기준선이다. 안정적인 백분위 성능이나 부하 수용량을 입증한 것으로 보고하지 않는다. 성능 통과 목표는 요구사항 확정 후 적용한다.
7. 커버리지는 통과율과 별개로 보고한다. 실행 커버리지=(통과+실패)/계획된 적용 가능 사례, 통과율=통과/(통과+실패). 차단·미실행·기준 미확정 수를 함께 공개한다.
8. 핵심 역할·흐름의 필수 사례가 차단되면 전체 합격을 선언하지 않는다. 재현된 결함은 회귀 사례로 남기고 동일 기준 리비전에서 재실행한다.

이번 개정은 테스트 기준 문서만 변경했다. 기능 구현·디자인 기준 변경 및 테스트 실행은 하지 않았다.
